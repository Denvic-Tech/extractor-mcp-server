# Источник «Запрос»: сегменты и параметры очереди

## Что получает помощник

Пользователь передает готовый запрос 1С с параметрами или без них. Его можно
получить и из СКД выбранного отчета. Отсутствие параметров не препятствует
созданию источника: после выбора сегментов агент добавляет их по смыслу. Сохраняй состав данных, вычисления, соединения
и фиксированные отборы.
Задача - связать согласованные сегменты с параметрами готового запроса и очередью.
Экстрактор выполняет один и тот же запрос для каждой записи очереди, подставляя
параметры соответствующего сегмента. MCP и DCC v2 используют одинаковое определение
проекта; DCC доставляет его в 1С через существующую очередь команд.

## Порядок действий

1. Выбери базу и маршрут, выполни readiness и проверь capability `query_sources`.
   Без нее источник «Запрос» недоступен. Не заменяй его источником «Обработчик»,
   исполнением BSL или неподдерживаемым маршрутом. Подключение и приемник выбирай
   по общему порядку настройки проектов.
2. Получи текст запроса. Если он уже передан, не проси его снова. Исследуй
   назначение запроса, его источники и существующие параметры. Если параметров
   нет, не требуй от пользователя самостоятельно параметризовать запрос. Уточни
   только неизвестные значения фиксированных параметров. Список значений
   фиксированного параметра сам по себе не является сегментированием.
3. Используй тот же диалог выбора сегментов, что для объектов: сначала предложи
   подходящие варианты, включая полную выгрузку без сегментов, затем согласуй выбор.
   Согласуй регулярную и начальную роли, а `extended` - при необходимости.
   Сохраняй принятые решения, типы ссылок, GUID и выбранную пакетизацию.
   Для автоматического Query допустима одна ось; несколько групп требуют
   явно настроенного обработчика или готового проекта, как описано ниже.
   Для `СрезПоследних` первым вариантом предложи `Месяц`. Дату сегмента
   явно приводи к согласованной границе периода в параметрах виртуальной таблицы.
4. Получи штатный список сущностей готового запроса через помощник Query.
   Если нужны очередь или отслеживание изменений, установи, набор данных какой сущности действительно ограничен параметром
   в виртуальной таблице или условии отбора. Согласуй ее как владельца `object`.
   `segmentation[].field` - подтвержденное поле владельца, а не псевдоним колонки.
5. После выбора сегментов используй подходящие существующие параметры либо
   сам добавь недостающие параметры и ограничения по смыслу. Затем свяжи каждый
   выбранный сегмент с его параметром запроса. Штатное имя группировки
   образуется из пути поля без точек и имени функции. Например, для поля `Период`
   и функции `Месяц` это `ПериодМесяц`. В `queryParameterNames` ключом служит
   штатное имя, значением - точное имя параметра запроса без `&`:
   `{"ПериодМесяц":"хПериод"}`. Имена в запросе, очереди и сопоставлении должны
   совпадать после применения этой связи.
6. Адаптируй только ограничения выбранного сегмента. Для регистров предпочитай
   параметры виртуальной таблицы: например, границы `.Обороты(...)`. Для
   справочников и документов используй условия отбора. Условия добавляй с учетом
   существующих условий, скобок и нужной ветви пакета. Не выполняй слепую замену
   текста и не ограничивай вспомогательные данные, нужные для расчета сегмента.
7. Перед выбором обработчика подтверди включенную сущность и ее параметрический
   отбор. Остальные обнаруженные сущности сохраняй в штатном списке выключенными.
   Настраивай обработчик только после этого выбора. Проверь, что запрос возвращает
   согласованный результат сегмента, включая необходимые данные обогащения.
8. Передавай фиксированные значения в `queryParameters`, отдельно от параметров
   сегмента. Не передавай их как текст BSL, SQL или сериализованный native-шаблон.
9. Создавай проект существующим `create_project(definition=..., operation_id=...)`
   для SQL. Для приемников-очередей сохраняй существующий preview/plan порядок.
   После записи перечитай проект и схему приемника: проверь тип источника,
   параметры, флаги сегментов, имена колонок и настройки строки.
10. Инициализация очереди и запуск выгрузки - отдельные действия. Выполняй их
    только в уже разрешенном пользователем объеме. Проверяй результат по исходным
    идентификаторам операций и задач. Принятая команда не доказывает успешную выгрузку.

## Сущности запроса: сначала отбор через параметр, затем обработчик

Используй существующий механизм помощника Query: он получает из запроса все
сущности и формирует штатный список связанных объектов. Наличие в этом списке
не означает включенное отслеживание. Не создавай отдельную схему дополнительных
источников и не заменяй настройки Query искусственной настройкой объекта.

Для согласованной полной выгрузки без очереди и отслеживания не включай сущности
ради назначения обработчика и не добавляй параметры только для этого. Следующий
порядок относится к выбору включенной сущности для очереди и изменений.

1. Для каждой найденной сущности проверь, можно ли ограничивать ее набор данных
   через параметр: границами виртуальной таблицы, условием `ГДЕ` или другим
   реальным отбором. Само упоминание параметра в расчете этого не доказывает.
2. Согласуй выбранную сущность и передай ее как `object`. Это единственный
   явно выбранный владелец параметрического отбора в текущем входном контракте.
   Найденные зависимые сущности для обогащения оставь выключенными. Сторона
   соединения не критерий: справа в `JOIN` тоже может быть сущность с реальным
   параметрическим отбором, которую нужно рассмотреть при выборе владельца.
3. Покажи штатный список с признаками включения, выбранный отбор и остальные
   зависимости. Только затем настрой подходящий штатный обработчик Query для
   включенной сущности. Выбор обработчика не заменяет доказательство отбора.
   Сохраняй этот выбор при обновлении проекта; новая колонка или `JOIN` сами
   по себе не расширяют отслеживание.
4. Отдельно назначь роли параметров очереди через существующую сегментацию.
   Фиксированный параметр в `ГДЕ`, например `&Организация`, может управлять
   отбором набора данных, но не становится из-за этого сегментом очереди.
   Параметр в `ВЫБОР`, вычислении или проекции без отбора не ограничивает набор
   данных: например, `&ЭтоТовар` и `&СобственныеРазработки` в расчетах не дают
   основания включить сущность. Проверяй фактическое место использования.

Пример: первый пакет получает `ВыручкаИСебестоимостьПродаж.Обороты` за границы
месяца по `&хПериод` и помещает результат в `Продажи`. Второй пакет присоединяет
`ДоговорыКонтрагентов.ДополнительныеРеквизиты` и `Партнеры`. Если они нужны только
для обогащения, включена одна сущность - регистр оборотов; обе зависимости
остаются в штатном списке выключенными. Расчетные параметры `&ЭтоТовар` и
`&СобственныеРазработки` не меняют этот выбор.

| Сущность в штатном списке | Управляемый отбор | Включение |
|---|---|---|
| `ВыручкаИСебестоимостьПродаж` | Границы оборотов по `&хПериод` | Да, выбранный `object` |
| `ДоговорыКонтрагентов.ДополнительныеРеквизиты` | Только присоединение для обогащения | Нет |
| `Партнеры` | Только присоединение для обогащения | Нет |

Для Query с сегментами используй `object`, `segmentation`, `queryParameterNames`
и `queryParameters`. Для полного Query с `segmentation: []` поле `object` не передавай. Отдельных полей списка дополнительных источников или
переопределения инициализатора нет. Штатный список сущностей обнаруживается
средствами Query, а не регулярными выражениями агента или API. В прямом MCP
и DCC v2 действуют одинаковые правила выбора и проверки.

При проверке сохраненного проекта читай `sourceSettings.relatedEntities`, если
он возвращается методами базы: включение, `handlerKind`, `handler` и параметры
обработчика. Это данные только для чтения, не входное поле создания проекта.

Настройка источника Query содержит текст запроса и настройки компоновки данных.
Для нее используй соответствующие штатные обработчики Query. Не применяй
обработчик `ПоНаборуДанных`, предназначенный для объектной настройки, к Query
путем подмены структуры источника. Отдельный обязательный override штатного
инициализатора для зависимостей запроса не требуется.

## Если готовый запрос не содержит параметров

Параметризацию выполняет агент при подготовке `queryText`, а не пользователь
и не автоматическая замена текста на сервере. Действуй по ветке дерева:

1. Исследуй исходный текст и метаданные: что возвращает результат, какие
   источники, временные таблицы, соединения и отборы обеспечивают расчет.
   Сначала предложи подходящие варианты сегментов и согласуй выбор и роли.
2. Для каждого выбранного сегмента найди место ограничения. В регистре используй
   соответствующие аргументы виртуальной таблицы. Для документа или справочника
   добавь условие к существующему `ГДЕ` через `И`, сохранив группировку скобками.
   Если `ГДЕ` нет, добавь его в нужную часть запроса. В пакете или объединении
   согласуй ограничения необходимых ветвей, не отсекая вспомогательные данные.
3. Выбери понятное имя параметра, проверь отсутствие конфликта с имеющимися
   именами и передай связь через `queryParameterNames`. Для месяца по `Период`
   это `ПериодМесяц`, для дня - `ПериодДень`. Не объявляй сегментный параметр
   одновременно фиксированным в `queryParameters`. Если параметры уже есть,
   сохрани подходящие имена, их назначение и фиксированные бизнес-отборы.
4. Сохрани поля результата, расчеты и детализацию. Явные даты и другие
   ограничения исходного запроса не отменяй автоматически: установи, какие
   из них задают выбранный сегмент, а какие являются фиксированным условием.
   При смысловой неоднозначности уточни ее, предложив конкретные варианты.
   Подготовленный запрос должен ограничивать выбранный сегмент, а итог всех
   требуемых сегментов - сохранять согласованный состав результата.
5. Проверь синтаксис и параметры подготовленного текста поддержанным способом,
   затем записанный маппинг и роли. В разрешенном тестовом прогоне сравни данные
   сегмента и повторной выгрузки, а не только ответ о принятии команды. Если
   выполнить проверку нельзя, назови непроверенную часть; не объявляй ее успешной.

Примеры ниже показывают изменяемые фрагменты. Остальные части готового запроса
сохраняются; исходные и выходные имена подтверждаются в выбранной базе.

## Параметры источника

- `queryText` - готовый текст запроса 1С; переключает источник на «Запрос».
- `segmentation` - прежний массив сегментов с явными Boolean `regular`,
  `extended`, `initialization`. Для запроса массив обязателен; `[]` означает
  выбранную выгрузку без сегментов. Старые `segment`/`segmentField` с ним не смешивай.
- `queryParameterNames` - необязательное сопоставление штатных имен группировок
  с именами параметров готового запроса. Без переименования сохраняются штатные имена.
- `queryParameters` - необязательный массив фиксированных значений. Каждый элемент
  содержит `name`, `type`, `value`. Дополнительный `object` нужен только для
  `reference` и `enum`. Сегментный и фиксированный параметры не должны совпадать.

| type | value | object |
|---|---|---|
| `string` | Строка, включая пустую | Не передается |
| `number` | Конечное число, включая ноль | Не передается |
| `boolean` | `true` или `false` | Не передается |
| `date` | Локальная дата `YYYY-MM-DDTHH:MM:SS` | Не передается |
| `reference` | UUID ссылки | Например, `Справочник.Склады` |
| `enum` | Имя значения перечисления | Например, `Перечисление.ТипыНоменклатуры` |

`value` может быть непустым массивом значений указанного типа. Для даты передавай
время базы 1С без суффикса часового пояса. `null` не является фиксированным значением;
неиспользуемые свойства опускай. Для ссылок не передавай представление вместо UUID.

## Пример: месячные сегменты регистра

В запросе ниже `&хПериод` берется из очереди. Границы периода устанавливаются в
параметрах виртуальной таблицы. `ПериодМесяц` остается именем группировки объекта,
а связь с именем параметра указана явно.

```json
{
  "object": "РегистрНакопления.Продажи",
  "projectName": "Продажи запросом",
  "connectionName": "PostgreSQL",
  "tableName": "sales",
  "queryText": "ВЫБРАТЬ Продажи.Номенклатура КАК Номенклатура, Продажи.КоличествоОборот КАК Количество ИЗ РегистрНакопления.Продажи.Обороты(НАЧАЛОПЕРИОДА(&хПериод, МЕСЯЦ), КОНЕЦПЕРИОДА(&хПериод, МЕСЯЦ), , ) КАК Продажи",
  "segmentation": [
    {"field":"Период","segment":"Месяц","regular":true,"extended":false,"initialization":true}
  ],
  "queryParameterNames": {"ПериодМесяц":"хПериод"}
}
```

Имена регистра, полей и подключения здесь иллюстративные. Сначала подтвердите их
в выбранной базе. Обнаруженные присоединенные объекты сохраняй в штатном списке,
но включай только согласованного владельца с реальным отбором по параметру.
Данные обогащения не должны автоматически создавать обработчики изменений.

## Пример: цены на конец месяца через «СрезПоследних»

Для `РегистрСведений.<Имя>.СрезПоследних` первым предложи сегмент **Месяц**.
Если пользователь уже выбрал месяц, сохрани выбор. Уточни роли сегмента и дату
среза внутри месяца. Для цен на конец месяца нормализуй параметр явно.
Если исходный фрагмент не параметризован:

```text
РегистрСведений.ЦеныНоменклатуры.СрезПоследних(, ) КАК Цены
```

После выбора месяца добавь параметр в дату виртуальной таблицы:

```text
РегистрСведений.ЦеныНоменклатуры.СрезПоследних(
    КОНЕЦПЕРИОДА(&ДатаСреза, МЕСЯЦ), ) КАК Цены
```

Если в результате нужна колонка даты среза, используй ту же границу периода.
Пример готового запроса с такой колонкой:

```text
ВЫБРАТЬ
    Цены.Период КАК Период,
    Цены.Номенклатура КАК Номенклатура,
    Цены.Характеристика КАК Характеристика,
    Цены.ВидЦены КАК ВидЦены,
    Цены.Цена КАК Цена,
    Цены.Упаковка КАК Упаковка,
    КОНЕЦПЕРИОДА(&ДатаСреза, МЕСЯЦ) КАК ДатаСреза
ИЗ
    РегистрСведений.ЦеныНоменклатуры.СрезПоследних(
        КОНЕЦПЕРИОДА(&ДатаСреза, МЕСЯЦ), ) КАК Цены
```

Источник значений очереди выбирается по обычному порядку для объектов. Для
поля `Период` и сегмента `Месяц` свяжи группировку `ПериодМесяц` с параметром
`ДатаСреза`. Например, после согласования одинакового месячного сегмента для
регулярной и начальной выгрузки используется такой фрагмент определения:

```json
{
  "object": "РегистрСведений.ЦеныНоменклатуры.СрезПоследних",
  "segmentation": [
    {"field":"Период","segment":"Месяц","regular":true,"extended":false,"initialization":true}
  ],
  "queryParameterNames": {"ПериодМесяц":"ДатаСреза"}
}
```

`ДатаСреза` - параметр из очереди, а не фиксированный `queryParameters`.
Псевдоним выходной колонки `ДатаСреза` не является полем метаданных для
`segmentation[].field`. Поле `Период` результата обозначает дату исходной записи
цены и может относиться к прошлому месяцу. Не добавляй отбор этого поля только
текущим месяцем: срез должен сохранять ранее установленные действующие цены.
Дата, выведенная в колонке `ДатаСреза`, должна совпадать с фактической датой
виртуальной таблицы. Для среза на начало месяца согласованно используй
`НАЧАЛОПЕРИОДА` в обоих местах. Не меняй дату среза молча.

## Обороты регистра: месяц или день в параметрах виртуальной таблицы

Исходный фрагмент без параметризации может выглядеть так:

```text
РегистрНакопления.ДоходыИРасходы.Обороты(, , Регистратор, )
    КАК ДоходыИРасходыОбороты
```

После выбора месячного сегмента добавь параметр и обе границы месяца:

```text
РегистрНакопления.ДоходыИРасходы.Обороты(
    НАЧАЛОПЕРИОДА(&ПарамДата, МЕСЯЦ),
    КОНЕЦПЕРИОДА(&ПарамДата, МЕСЯЦ),
    Регистратор, ) КАК ДоходыИРасходыОбороты
```

Связь с очередью: поле `Период`, сегмент `Месяц`,
`queryParameterNames: {"ПериодМесяц":"ПарамДата"}`.

Если пользователь выбрал сегменты по дням, измени единицу в обеих границах:

```text
РегистрНакопления.ДоходыИРасходы.Обороты(
    НАЧАЛОПЕРИОДА(&ПарамДата, ДЕНЬ),
    КОНЕЦПЕРИОДА(&ПарамДата, ДЕНЬ),
    Регистратор, ) КАК ДоходыИРасходыОбороты
```

Связь с очередью: поле `Период`, сегмент `День`,
`queryParameterNames: {"ПериодДень":"ПарамДата"}`.

Третий аргумент `Регистратор` задает детализацию результата и сохраняется при
выборе месяца или дня. Не заменяй его на `Месяц` только из-за месячных сегментов.
Поля выборки, ресурсы, измерения и остальные отборы готового запроса сохраняй.
Не заменяй ограничение параметрами виртуальной таблицы внешним условием `ГДЕ`.
Начало и конец периода используй согласованно с выбранным сегментом; не оставляй
прямую дату из очереди вместо одной из границ. Наличие регистра, его полей и
поддерживаемой периодичности результата подтверди в выбранной базе до создания.

## Граница автоматического построения Query: одна ось

Новый Query автоматически создается с одной группировкой и одним параметром
сегмента. Ее флаги `regular`, `extended`, `initialization` независимы и задают
роли одной выбранной оси. Например, месяц может использоваться в регулярной
и начальной выгрузке. Наличие трех флагов не означает три разных группировки.

Если автоматическому построителю передано больше одной группы, он возвращает
`QUERY_NATIVE_SINGLE_AXIS_REQUIRED`. Не обещай автоматическое создание сочетаний
«день регулярно, месяц при инициализации», нескольких полей или других кортежей
сегментов. Для такой задачи нужен явно настроенный собственный обработчик очереди
или уже подготовленный штатными средствами проект. Согласуй этот путь; не
угадывай сочетания и не строй декартово произведение. Текст собственного
обработчика не передавай через неподдержанные поля MCP.

Ограничение относится к автоматическому построению нового источника Query.
Оно не запрещает чтение, запуск и изменение сопоставления полей уже вручную
настроенных Query-проектов с собственными обработчиками. Не перестраивай такой
проект и не отклоняй `fieldChanges` только из-за нескольких сохраненных осей.
Для ветви «Объекты» существующие возможности группировок и разных ролей сохраняются.

Для полного Query без сегментации передавай `segmentation: []` и не передавай
`object`: искусственный владелец не нужен. Не требуй параметризованного отбора
или обработчика ради полной выгрузки. `object` обязателен для Query с сегментами
и обозначает явно выбранного владельца параметрического отбора.

## Пример: условие для документа

Для согласованного сегмента «День» по полю `Дата` штатное имя - `ДатаДень`.
Если готовый запрос использует `&ДатаВыгрузки`, передай
`queryParameterNames: {"ДатаДень":"ДатаВыгрузки"}`. Ограничение в запросе:

```text
ГДЕ Документы.Дата МЕЖДУ НАЧАЛОПЕРИОДА(&ДатаВыгрузки, ДЕНЬ)
    И КОНЕЦПЕРИОДА(&ДатаВыгрузки, ДЕНЬ)
```

Для табличной части путь очереди может быть `Ссылка.Дата`. Для ссылочного сегмента
используй типизированный параметр ссылки и выбранную пакетизацию по общим правилам
объектов. Не заменяй ссылку ее строковым GUID в условии запроса 1С.

## Справочник: сегменты по первой букве или первым двум буквам

Строковые сегменты должны одинаково обрабатывать прописные и строчные буквы.
Приводи к нижнему регистру обе стороны сравнения: подстроку поля справочника
и параметр сегмента из очереди. Например, для первых двух букв:

```text
ГДЕ НРЕГ(ПОДСТРОКА(Н.Наименование, 1, 2)) = НРЕГ(ВЫРАЗИТЬ(&Префикс КАК СТРОКА(2)))
```

Для первой буквы используй ту же конструкцию с длиной `1`:

```text
ГДЕ НРЕГ(ПОДСТРОКА(Н.Наименование, 1, 1)) = НРЕГ(ВЫРАЗИТЬ(&Префикс КАК СТРОКА(1)))
```

В этих примерах `ВЫРАЗИТЬ` явно задает строковый тип аргумента `НРЕГ`:
`СТРОКА(1)` для первой буквы и `СТРОКА(2)` для первых двух. Это уточнение
используй при подготовке запроса через СКД. Проверяй выражение в штатном пути
выгрузки: успешный прямой запуск объекта `Запрос` сам по себе не подтверждает
обработку параметра после формирования запроса СКД. Запись `НРЕГ(&Префикс)`
может работать при прямом запуске; общего запрета такой записи нет.

Сохраняй согласованную длину сегмента и выбранное поле. Не меняй «Первые две буквы»
на «Первую букву» и не расширяй отбор до совпадения произвольного начала строки.
Для имени `Ab...` очередь и условие должны обозначать тот же сегмент, что для
`ab...`. Аналогично `АБ...` и `аб...` должны попадать в общий сегмент `аб`.
Штатное формирование очереди уже нормализует строковый ключ через нижний регистр
и удаление завершающих пробелов; собственный обработчик только ради этого не нужен.

Пустая строка `""` - допустимое значение сегмента, а не отсутствие сегментирования.
При `Префикс = ""` условие сравнения остается включенным и выбирает только строки
с пустой подстрокой. Нельзя добавлять `&Префикс = "" ИЛИ ...`, пропускать пустые
ключи очереди или трактовать такой сегмент как «выгрузить всё». В запросе с разными
ролями отличай `НЕОПРЕДЕЛЕНО` у неактивного параметра от действительного сегмента
`""`; для выбора роли не используй проверку на непустую строку.

Перед использованием `НРЕГ` в языке запросов проверь версию платформы и режим
совместимости выбранной базы, затем проверь синтаксис подготовленного запроса
штатными средствами 1С. Эта функция языка запросов появилась в платформе 8.3.20;
пример нельзя автоматически применять к 8.3.5. Сведения о добавлении функции
приведены в [описании изменений платформы 8.3.20](https://dl03.1c.ru/content/Platform/8_3_20_1710/1cv8upd_8_3_20_1710.htm).
Если функция недоступна, сохрани требование сравнения без учета регистра и подбери
поддерживаемый вариант с проверкой в целевой базе. Не переходи молча на сравнение
с учетом регистра.

Для старой платформы проверь штатное сравнение строк в выбранной базе. Если
`ПОДСТРОКА` с параметром одинаково выбирает прописные и строчные варианты,
допустимо условие без недоступной функции языка запросов:

```text
ГДЕ ПОДСТРОКА(Н.Наименование, 1, 2) = &Префикс
```

Ключ сегмента и партиция при этом по-прежнему приводятся к нижнему регистру
средствами встроенного языка в EPA. Проверь оба регистра латиницы и кириллицы,
длину `1` и `2`, пустую строку и сохранность соседнего сегмента. Наличие функции
`НРег` во встроенном языке не подтверждает поддержку `НРЕГ` в языке запросов.
Если сравнение в целевой базе учитывает регистр, этот вариант не подходит.

Для проверки подготовь данные с латинскими `Ab`/`ab`, кириллическими `АБ`/`аб`,
именем из одного символа и пустым именем. Проверь отдельно пустой сегмент и соседний
префикс, например `ac`: обновление сегмента `ab` не должно затрагивать `ac`.
Проверка передачи текста через MCP/DCC сама по себе не подтверждает отбор данных;
правильность и повторную выгрузку сегмента проверяй на выполнении запроса в 1С.

## Пример: полная выгрузка с фиксированным отбором

```json
{
  "projectName":"Номенклатура запросом",
  "connectionName":"PostgreSQL",
  "tableName":"items",
  "queryText":"ВЫБРАТЬ Н.Ссылка КАК Ссылка, Н.Наименование КАК Наименование ИЗ Справочник.Номенклатура КАК Н ГДЕ Н.ПометкаУдаления = &Удаленные",
  "segmentation":[],
  "queryParameters":[{"name":"Удаленные","type":"boolean","value":false}]
}
```

Здесь параметр `Удаленные` фиксирован. Запрос выполняется целиком; очередь сегментов
и флаги сегментных колонок ему не назначаются только из-за наличия параметра.

## Проверка согласованности

После записи перечитай штатный список сущностей, признаки включения и назначенные
обработчики. Включен только согласованный владелец с отбором через параметр;
зависимости для обогащения сохранены выключенными. После инициализации проверь
очередь выбранных сегментов и параметры в реальной выгрузке. Отбор должен
сохранять расчеты и необходимые зависимости во всех нужных ветвях запроса.
Для `КОЛИЧЕСТВО(*)` (`COUNT`) без группировки пустой входной набор может дать
строку со счетчиком `0`; такая строка сама по себе не означает ошибку выгрузки.

Проверь точные имена и типы параметров, соответствие группировкам очереди и роли
колонок приемника. В сложном запросе проверь каждый источник, который поставляет
сегменты. Повторная выгрузка выбранного сегмента должна обновлять его данные,
сохранять соседние сегменты и корректно обрабатывать пустой результат.
Проверку записи настроек, создания таблицы и фактической выгрузки учитывай отдельно.

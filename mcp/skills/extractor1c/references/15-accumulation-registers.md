# Регистры накопления и связанные сущности

Используй этот порядок, когда пользователь просит подготовить, создать или дополнить выгрузку регистра накопления.

## Анализ связей

По умолчанию предпочитай источник `РегистрНакопления.<Имя>.Обороты`.
Сначала подтверди его наличие и поля через MCP. Анализ связей выполняй по
основному регистру, а поля выгрузки выбирай по виртуальной таблице: её ресурсы
и детализация могут отличаться. Проверяй периодичность и зерно результата
в предпросмотре; сегмент `День` сам по себе не задаёт периодичность оборотов.
Если нужны исходные движения, остатки или явно другой источник, используй
соответствующий источник вместо Обороты. Не подменяй недоступную виртуальную
таблицу молча и не добавляй суффикс без проверки метаданных.

1. Вызови `analyze_reference_graph(object=...)`: сервер выделяет все ссылочные поля головной сущности и возвращает граф с точными целевыми метаданными и путями.
2. Найди регистры сведений, связанные с регистром накопления через его измерения или реквизиты. Поле или объект с именем, начинающимся на `Ключ`, - только подсказка для поиска, а не доказательство связи. Учитывай связи с другими именами и подтверждай связь типами и метаданными через MCP.
3. Сервер раскрывает непериодические регистры сведений автоматически. Периодические регистры пропускаются с причиной `periodic_register`, даже при явном запросе раскрытия.
4. Покажи пользователю два раздельных списка:
   - прямые ссылочные поля регистра накопления;
   - ссылочные поля, доступные через каждый подтверждённый связанный регистр сведений.

Для косвенной связи укажи путь, например `РегистрНакопления.КлючАналитики -> РегистрСведений.АналитикаУчета -> Номенклатура`, и поля соединения выгруженных таблиц. Если метаданных недостаточно, явно обозначь связь как предположение.

Ссылка на ключ аналитики может вести в обычный справочник. Раскрывай его по
`expand_paths`, например `АналитикаУчетаНоменклатуры.Номенклатура`, чтобы получить
единицу измерения и вид номенклатуры. Не выводи связь с регистром по одному имени ключа.
Не считай `join` готовым соединением без проверки ключей; для составного типа
сохраняй тип каждой ветви из `steps`. Проверяй `complete`, `truncated`, `warnings`
и `unresolvedExpandPaths`, прежде чем утверждать полноту анализа.

## Согласование состава выгрузки

После показа связей спроси, какие связанные справочники и документы выгружать совместно с регистром накопления отдельными строками одного проекта. Включи как прямые сущности, так и найденные через связанные регистры сведений.

Не создавай дополнительные строки до ответа пользователя. Связанные регистры сведений также предлагай отдельными строками, когда они нужны для воспроизводимого соединения косвенных связей.

До первой записи выведи компактный нумерованный список всех предлагаемых строк проекта: объект, таблицу назначения и сегмент партицирования. Запроси подтверждение всего списка. Если пользователь уже перечислил сущности и параметры, считай состав подтверждённым и не задавай тот же вопрос повторно.

## Выбор сегментов партицирования

Спрашивай и показывай пользователю **сегмент партицирования**, а не «группировку». Если пользователь не задал другое:

- для регистра накопления используй сегмент `День`;
- для справочника или документа спроси о выборе по [16-catalog-document-segments.md](16-catalog-document-segments.md); автоматического выбора префикса или дня нет;
- для непериодического регистра сведений используй сегмент `По значению` по подтверждённому ссылочному ключу.

Задавай `maxItemsPerBatch` по смыслу сегмента:

- `0` для сегментов по периоду (`День`, `Месяц`);
- `0` для сегментов по префиксу строки (`Первые две буквы`);
- `1000` только для сегмента `По значению` по подтверждённому ссылочному полю; для выбранного `Ссылка` справочника или документа используй упаковку по 1000 элементов.

Не назначай `1000` только по виду объекта или отсутствию периодичности. Сначала подтверди по метаданным ссылочный тип поля и связь с основной строкой. Поле с префиксом `Ключ` - лишь подсказка для поиска. Значение `1000` означает размер упаковки элементов при выгрузке, а не число потоков или общий лимит строк.

Если у строки с сегментом `Первые две буквы` задан непустой `selectedFields`, включи фактически выбранный параметр: `Параметр.НаименованиеПервыеДвеБуквы` либо `Параметр.КодПервыеДвеБуквы`. Для `Ссылка` сохраняй `Параметр.Ссылка`. После `verify_project` проверь поле сегмента и упаковку.

## Поэтапная запись строк

После подтверждения сохраняй всё в одном проекте и записывай последовательно:

1. Подготовь и проверь через `preview_project` только строку основного регистра накопления. После подтверждения создай проект через `create_project(planId, operationId)`, затем вызови `verify_project_summary`.
2. Для каждой следующей подтверждённой сущности раскрывай поля непосредственно перед добавлением и получай свежий `expectedState` через `verify_project`.
3. Вызови `preview_project` для добавления ровно одной строки, после подтверждения добавь её через `update_project(planId, operationId)` и снова вызови `verify_project_summary`.
4. Переходи к следующей строке только после успешной проверки предыдущей. При ошибке остановись, сообщи, какие строки уже записаны, и не повторяй запись вслепую.
5. После последней строки ещё раз проверь весь проект: точный набор строк, таблицы, поля, GUID-типы, сегменты и общее число сопоставлений.

Не создавай все строки одним групповым запросом. Под «коммитом строки» понимай успешный `update_project` и последующий `verify_project`, а не Git-коммит.

## Поля связанных объектов по умолчанию

Не используй пустой `selectedFields` для связанных справочников и документов: пустое значение означает выгрузку всех полей.

Перед формированием `selectedFields`:

1. Вызови `describe_object_fields` для объекта.
2. Составь минимальный список кандидатов для его вида.
3. Пересеки список кандидатов с фактическими именами полей из метаданных.
4. Добавь только найденные поля и штатно формируемые вычисляемые или служебные поля, источник которых существует.

Не используй ошибки `preview_project` для последовательного обнаружения отсутствующих реквизитов. Предпросмотр проверяет уже собранное определение проекта.

### Справочники

Для справочника по умолчанию выбирай только:

- `Ссылка` как GUID-колонку;
- `Наименование`;
- `Код`.

Добавляй только реально существующие поля. В частности, добавляй `Код` только при его наличии в результате `describe_object_fields`. Отсутствие стандартного поля в метаданных допустимо и не должно блокировать создание строки. Вычисляемое GUID-поле для ссылки добавляй только тогда, когда исходное ссылочное поле существует. Также:

- для контрагентов всегда добавляй `ИНН`, `КПП` и `ОГРН`, если они существуют;
- для номенклатуры всегда добавляй `Группа` и `ЕдиницаИзмерения`, если они существуют;
- для любого справочника всегда добавляй `Группа`, если такое поле существует;
- добавляй ссылочные поля, необходимые для соединения выбранных сущностей, даже если они не входят в основной набор. Например, для договоров контрагентов включай ссылки на организацию и контрагента, когда эти справочники входят в проект.

Не подменяй отсутствующее поле похожим без явного указания пользователю. Если используется функциональный аналог с другим именем, покажи найденное имя и предложи его включить.

### Документы

Для документа по умолчанию выбирай только:

- `Ссылка` как GUID-колонку;
- `Номер`;
- `Дата`;
- `Проведен`;
- `ПометкаУдаления`;
- `Представление`.

Добавляй только поля, реально доступные по метаданным или формируемые штатным механизмом проекта. Не включай все поля документа автоматически.

До выбора сегмента прочитай метаданные документа и спроси: по периоду (День) или по Ссылка. Если выбран период, проверяй поля так. Если поле `Дата` существует и имеет тип `Дата`, используй сегмент `День` по полю `Дата` и `maxItemsPerBatch: 0`. Если `Дата` отсутствует, но поле `Период` существует и имеет тип `Дата`, используй сегмент `День` по полю `Период` и `maxItemsPerBatch: 0`. Если выбрана ссылка: `segment: По значению`, `segmentField: Ссылка`, `maxItemsPerBatch: 1000`. Не угадывай тип поля и не меняй выбранный режим молча.

При непустом `selectedFields` включай служебное поле `Параметр.<ИмяПоля>День`, только если его показывает `preview_project`. Например, для сегмента по `Дата` это `Параметр.ДатаДень`. Отсутствующее поле `Представление` допустимо: просто не добавляй его в `selectedFields`.

## GUID-колонки и типы

Для каждой ссылки включай штатное вычисляемое поле `УникальныйИдентификатор()` и через `guidColumnNames` задавай имя назначения в латинице по шаблону `<EntityName>Guid`, например `KontragentGuid`, `OrganizatsiyaGuid`, `DogovorGuid`. Имя должно отражать сущность, а не называться просто `SsylkaGuid`. При совпадениях добавь контекст роли или пути, чтобы имена оставались уникальными и однозначными.

### Единые имена ключей связи

До первого `preview_project` составь каноническую карту ключей для всех подтверждённых строк. Одна логическая связь должна иметь одно и то же имя GUID-колонки во всех участвующих таблицах: GUID ссылки в родительской строке и GUID поля `Ссылка` связанной сущности переименовывай одинаково. Например, `ОрганизацияГуид` регистра, `СсылкаГуид` справочника организаций и `ОрганизацияГуид` договора должны иметь имя `OrganizatsiyaGuid`.

Для связи через регистр сведений одинаково именуй ключ с обеих сторон, даже если исходные поля называются по-разному. Перед добавлением каждой строки сверяй её `guidColumnNames` с канонической картой, а после `verify_project` проверяй фактические имена колонок.

Не объединяй разные роли только из-за совпадения типа. Для нескольких ссылок на одну сущность используй имена с ролью или путём. Если составная ссылка не позволяет получить одинаковый ключ без ложного объединения, сообщи об ограничении до записи строки.

Для PostgreSQL и ClickHouse полагайся на штатный подбор подходящего типа Экстрактором 1С для вычисляемого поля `УникальныйИдентификатор()`. Не задавай тип вручную и не подменяй UUID строкой. Проверь тип в `preview_project` и `verify_project`; если он не соответствует нативному UUID-типу приёмника, сообщи пользователю.

# Сегментация API 3.3.1

Поддерживается Экстрактор 1С начиная с 3.16.1.xx. `segmentation` - массив группировок, а не объект с `mode`. Каждая группировка содержит обязательные `field`, `segment`, `regular`, `extended`, `initialization`.

Порядок записи зависит от приёмника. Для SQL при capability
`direct_sql_operations` передавай согласованное определение прямо в
`create_project`/`update_project` с `operation_id`, без обязательного preview.
Штатный помощник формирует поля и проверяет типы внутри этой операции;
после записи перечитай сохранённые роли, все поля и физическую схему.
Упоминания preview ниже описывают дополнительную диагностику SQL или
обязательный план для Kafka, AMQP и 1С Шины. Не вставляй скрытый preview RPC
перед каждым SQL-запуском. Если для явного `selectedFields` ещё неизвестны
штатные имена вычислений, прочитай существующий проект или используй
необязательный preview для определения имён; не угадывай их.

```json
{
  "segmentation": [
    {"field":"Регистратор","segment":"По значению","regular":true,"extended":false,"initialization":false},
    {"field":"Период","segment":"День","regular":false,"extended":true,"initialization":false},
    {"field":"Период","segment":"Месяц","regular":false,"extended":false,"initialization":true}
  ]
}
```

`field` - непустой подтверждённый путь поля; для табличной части документа дата шапки задаётся явно как `Ссылка.Дата`. `segment`: `По значению`, `Первая буква`, `Первые две буквы`, `Произвольная подстрока`, `Час`, `День`, `Неделя`, `Месяц`, `Квартал`, `Полугодие`, `Год`. Проверяй соответствие функции подтверждённому типу поля и сохранённым настройкам; preview используй при необходимости. Дополнительные настройки функции, которые не представлены контрактом, через этот запрос не задаются.

Три признака ролей имеют тип Boolean; у каждого элемента хотя бы один равен `true`. Одна группировка может участвовать в нескольких ролях. Массив содержит до 500 элементов; пустой массив явно не задаёт группировки. Не смешивай массив с `segment`/`segmentField`. Простой одно-сегментный запрос остаётся отдельным вариантом; новые многоролевые запросы формируй массивом. Объект `segmentation` с `mode` отклоняется.

Если пользователь ещё не выбрал сегмент партицирования, согласуй его до подготовки проекта: документ - день или ссылка; справочник - префикс наименования/кода или ссылка. Для ссылки используй `По значению`, поле `Ссылка` и `maxItemsPerBatch: 1000`; это размер упаковки, а не предел всей выгрузки. Для дня документа проверь `Дата`/`Период`; для табличной части - `Ссылка.Дата`. Поля с одинаковыми путём и функцией могут участвовать в нескольких ролях через один элемент с несколькими флагами.

Для подобных справочников по умолчанию предлагай расширенную схему: регулярная
выгрузка по `Ссылка`, `По значению`, упаковка `1000`; инициализация по
`Наименование`, `Первые две буквы`. Сначала подтверди поля и поддержку функций
в этой базе. Это предложение для справочников, а не правило для всех сущностей;
согласованный другой вариант сохраняй. Проверяй оба параметра и роли в маппинге.
Если публикация возвращает `sourceSettings.parameterSelection`, отдельно сверяй
фактический выбор полей СКД: одни grouping-галки его не подтверждают.

Хранение в текущем Экстракторе использует `ПараметрРегулярный`, `ПараметрРасширенный`, `ПараметрИнициализации`. Развилки хранения для предыдущих выпусков Экстрактора не используются. Роли группировки и галки сопоставления полей - разные представления: сверяй сохранённый источник и маппинг, не выводи роль из одной галки.

`selectedFields` должен сохранить фактические поля всех выбранных ролей, параметры сегмента и нужные GUID-вычисления. Для SQL используй прямую запись с проверенным составом; для Kafka, AMQP и 1С Шины сохрани точный `planId` предпросмотра. После записи выполни `verify_project_summary`. Не заменяй вручную настроенные роли простым запросом без согласованного изменения. Создание настроек не инициализирует очередь и не запускает выгрузку. При неопределённом результате сначала проверь операцию и состояние проекта; не повторяй запись с новым `operationId` вслепую.

## Табличная часть справочника: разные роли сегментов

Перед проверкой существующего проекта прочитай его актуальное имя, UUID,
подключение, grouping и fields через verify_project/verify_project_summary.
Сохраняй ручные изменения пользователя. После переименования проекта
используй новое имя для чтения и прежний UUID для статуса выполнения.

Проверенный вариант в локальной Denis, 11.10.2026:
`Справочник.Номенклатура.ДополнительныеРеквизиты`:

- регулярная выгрузка: `Ссылка`, «По значению», упаковка 1000;
- инициализация: `Ссылка.Наименование`, «Первые две буквы»;
- сопоставление: `Параметр.Ссылка` с regular-ролью и
  `Параметр.НаименованиеПервыеДвеБуквы` с initialization-ролью;
- сохранены GUID владельца и параметры группировок.

Это пример разделения ролей, а не обязательная схема для всех справочников.
Для любого подключения правило относится к любому выбранному полю сегмента,
фактически имеющему ссылочный тип по метаданным/native preview; `Ссылка` и
`Регистратор` - лишь примеры. Исходный типизированный параметр участвует в
отборе запроса 1С: не заменяй его GUID-выражением или GUID-строкой. После
получения значения штатная функция/модуль Э1С `УникальныйИдентификатор`
обрабатывает его тип и вычисляет GUID для SQL-поля соответствующей роли сегмента.
Вывод самой ссылки необязателен; показ/скрытие представления роль GUID не меняет.
Точную связь исходного поля, параметра, GUID-вычисления и SQL-роли читай из
сохранённых настроек `verify_project` либо необязательного native preview/get_project_plan: имя `Параметр.<Поле>` не конструируй по догадке.
Сохраняй штатные тип и длину GUID; галка «Экранировать» у GUID должна быть снята.
Даты, строки, числа, булевы значения и другие нессылочные типы этим правилом не меняй.
При прямом SQL после записи проверь фактическое поле роли через `verify_project`;
при выбранном preview проверь его и до записи. Описание контракта не заменяет проверку работающей базы.
В явном `selectedFields` сохраняй фактическое GUID-вычисление роли из
сохранённых настроек `verify_project` либо необязательного native preview/get_project_plan. Имя параметра в историческом примере не
заменяет текущее поле SQL-сегмента; имена вычислений не угадывай.

Путь через владельца (`Ссылка.Наименование`/`Ссылка.Код`) отличается от
реквизита самой табличной части. Роли regular и initialization выбираются
отдельно: нельзя выводить настройки инициализации из регулярной группировки.
После прямой SQL-записи сверяй обе роли и их поля сопоставления через `verify_project`; в режиме с preview дополнительно сверяй их с планом до записи.
Пустой набор сегментов или отсутствие строк в приёмнике сами по себе
не подтверждают корректную выгрузку.

Успешная выгрузка и состояние инициализации проверяются отдельно. Если API
вернул PREVIOUS_INITIALIZATION_UNKNOWN/BACKGROUND_JOB_NOT_FOUND, сначала
диагностируй исходную задачу; не очищай её статус и не запускай дубликат
для обхода блокировки. Точечное удаление зависшей записи возможно только
по явному указанию пользователя, после подтверждения отсутствия активного
фонового задания; это отдельная восстановительная операция. В этом примере ручная выгрузка succeeded и данные
в ClickHouse подтверждены, но более поздняя инициализация стала unknown.
Этот факт не доказывает причину прежней ошибки транзакции.

## Составные поля: сегменты и GUID

Составные поля никогда не выбирай как сегменты: запрет действует и для нескольких ссылочных типов, и для смеси ссылок с примитивами. До выбора проверь фактическое описание типов поля; для сегмента допускается один конкретный тип. Не перестраивай существующий проект автоматически: согласуй замену составного сегмента.

GUID любых составных полей вычисляй только штатной функцией Экстрактора 1С `УникальныйИдентификатор` в буфере. Не подменяй её SQL/query-функцией UUID или собственным конвертером. Правило действует для всех экспортируемых составных полей, включая поля без роли сегмента.

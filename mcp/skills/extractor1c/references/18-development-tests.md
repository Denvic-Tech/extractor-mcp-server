# Проверки разработки MCP 3.3.7 / EPA 3.3.5

Для `columnNames` проверь отсутствие ключа в старом запросе, одиночное и групповое
создание, вложенное definition, capability `column_names` до изменяющего вызова,
неверные идентификаторы, пересечение с guidColumnNames и итоговые коллизии.
Сокращение длинного SQL-имени должно происходить до штатной проверки драйвера;
источник, тип, GUID-вычисление и роли должны сохраняться. Живой прогон требует
применения EPA 3.3.5; локальная схема MCP не доказывает обновление базы.

Отчёты, результаты прогонов и настройки тестовых баз храни только локально в исключённых из Git файлах. Не добавляй их в коммиты и merge request.

После изменений кода MCP из каталога `mcp/` запускай `.\.venv\Scripts\python.exe -m pytest -q`. Проверяй массив сегментации, обязательные Boolean-роли, путь поля и все разрешённые функции, исключение объектного формата, preview/planId, идемпотентность операции и раздельные версии MCP 3.3.7 / ожидаемого контракта EPA 3.3.5.

Для `inspect_project_receiver` обязательны закрытая схема без SQL/приёмника override, UUID проекта, уникальные checks/поля, строгий целый лимит, явные поля и лимит для sample, максимум 64 поля. Проверь оба транспорта: direct HTTP использует только фиксированный `projects/verify` с внутренним `receiverInspection:true`, DCC - логический маршрут без признака. Прежний verify неизменен. Проверь отказ старой EPA и отсутствующего capability, изоляцию выбранной базы, отсутствие записи проекта/выгрузки, lossless строковое количество и `sourceEqualityVerified=false`. Полный прогон сохраняй отдельно от интеграционного результата живых баз.

Проверяй отдельно: несколько HTTP-баз из YAML; выбор base_id и изоляцию планов; обнаружение поддерживающих MCP коннекторов DCC и исключение несовместимых; отсутствие прямых вызовов публикации 1С в DCC-режиме; структурированный результат, отказ, таймаут и повторное чтение результата задачи.

После изменения формирования проектов или выгрузки нужна новая живая проверка на применённой сборке: справочник и его часть, документ и его часть, РН.Обороты, РС.СрезПоследних, ПВХ, перечисление, журнал проводок (основная таблица регистра бухгалтерии) и субконто. Журналы документов (`ЖурналДокументов.*`), включая `СкладскиеОрдера`, в тестовую матрицу не входят. Журнал проводок проверяется отдельно от нормализованной таблицы субконто: нужны период, регистратор, счета дебета и кредита и сумма. Сначала подтвердить readiness и доступный приёмник. Выполнять записи и запуск только в разрешённой пользователем тестовой базе. Успешное чтение метаданных не подтверждает создание проекта; completed операции не заменяет succeeded выгрузки. Не переиспользовать старую успешную квитанцию как доказательство новой сборки.


В отчёте указывать версии, конкретный артефакт, выполненные проверки, свежие задачи и ограничения. Недоступные проверки не считать пройденными.

## Проверка составных полей

Проверь отказ от выбора любого составного поля как сегмента, включая несколько ссылочных типов и смесь ссылок с примитивами. Для GUID всех экспортируемых составных полей проверь использование штатной функции Экстрактора 1С в буфере без SQL UUID; поле не обязано быть сегментом. Ранее описанные положительные сценарии составной сегментации отменены пользовательским правилом от 20.10.2026.

## Полный маршрут Помощника и фактическая выгрузка

Проверка общего helper отдельно не доказывает работу публичного EPA:
после Помощника API выполняет дополнительные проверки. Для исправления
сегментации проверь полный штатный маршрут создания, инициализацию,
реальную выгрузку и повторную выгрузку на применённом артефакте. Отдельный
preview используй для приёмников-очередей или явно выбранного чтения плана.
В разрешённой тестовой базе выполняй эту цепочку без дополнительных пауз
на согласование уже разрешённых шагов. Для SQL используй прямой режим
существующих инструментов при capability `direct_sql_operations`, без отдельного
preview RPC. Для Kafka, AMQP и 1С Шины сохраняй preview с `planId`. Успешным
итогом теста считается подтверждённая выгрузка и запрошенная сверка источника
с приёмником.

Если инженерная обработка вызывает фиксированный `EPA_Projects.ОбработатьJSON`,
сверяй её типизированный payload с полным wire-контрактом текущего MCP.
Минимальный ввод инструмента и передаваемый в EPA запрос могут отличаться:
`ProjectDefinition` добавляет обязательные Boolean `includeGuids` и
`includeMetadataTypes`. Ошибка схемы до Помощника не проверяет исправление
сегментации. Используй только фиксированные скомпилированные тестовые действия;
этот порядок не разрешает передавать исполняемый BSL через интеграцию.

Отрицательный тест должен подтверждать ожидаемую причину отказа. Один
HTTP-статус может означать другую ошибку; связывай безопасный `errorId`
с native-журналом, если он доступен. Отдельно проверяй `noExport` и все пять
`noEscape`, полный состав экспортируемых SQL-колонок, типы, точность и роли.
Отключённые строки сохраняй для проверки, не удаляй их молча из результата.

## Сохранённые поля: fieldChanges (MCP 3.3.7 / EPA 3.3.5)

Проверяй закрытые схемы source/target/noExport, сохранение false и пропуска,
запрет null и дополнительных SQL/BSL/connection override, коллизии имён,
отсутствующий source и отключение сегмента. Оба транспорта используют прежний
projects/update, обязательный operation_id и свежий expectedState. Без
field_mapping операция должна отказаться до изменяющего вызова.
В живой базе проверь обычную строку (Артикул -> Article), включение и отключение
представления ссылки с сохранением GUID, native-схему, фактическую выгрузку
и выборку новых колонок. Принятый patch не доказывает заполнение прежних данных.

# Проверка приёмника перед проектом и выгрузкой

Применяй к ClickHouse, PostgreSQL, MySQL, MS SQL и Apache Kafka при создании проекта, изменении его полей/таблицы/ключей и диагностике отказа. При запуске сохранённого проекта проверь соответствие сохранённого сопоставления физическому приёмнику; не переподбирай имена и типы заново.

## Порядок и границы

### Сначала проверить выбранное подключение

После выбора базы и подключения, до подготовки полей и предпросмотра проекта,
проверь соединение с приёмником именно со стороны исполняющей 1С и штатного
драйвера Экстрактора. Доступ с компьютера пользователя или MCP-сервера и
`readiness.ready=true` не подтверждают этот участок соединения.

Используй доступный поддержанный инструмент проверки подключения. Для уже
существующего проекта на том же подключении допустимо чтение схемы через
`inspect_project_receiver`, если оно завершилось успешно. Не создавай
диагностический проект и не запускай выгрузку ради проверки соединения.
Если отдельной проверки нет в MCP и нет подходящего сохранённого проекта,
сообщи об ограничении и попроси выполнить штатную проверку подключения в 1С;
не выдумывай инструмент и не подменяй проверку произвольным SQL/BSL.

При таймауте, отказе авторизации или другой ошибке останови зависимую
подготовку проекта. Укажи выбранное подключение, сервер 1С, адрес/порт
приёмника и исходную ошибку с errorId, если эти сведения известны. Не меняй
приёмник молча и не повторяй preview с другими полями или сегментами для
обхода сетевого отказа. Продолжай после успешной повторной проверки либо
явного выбора пользователем другого подключения.

### Проверка состава и схемы

1. `list_bases` -> выбранный `base_id` -> `readiness` -> `list_connections`. Зафиксируй фактические версии 1С/API и тип подключения, транспорт (DLL/ADO/HTTP/Native/Proxy), доступные возможности. `ready=true` с предупреждением о несовпадении контрактов не доказывает готовность записи. Не устанавливай отсутствующие компоненты и не меняй настройки сервера молча.
2. Прочитай метаданные и настройки существующего проекта. Для нового - `preview_project`/`preview_project_template`, затем **все страницы** `get_project_plan`: source, target, type, precision, scale, nullable и роли сегментов. Удобный JSON-шаблон не предоставляет дополнительных возможностей сверх схемы API.
3. Проверяй фактические имена после транслитерации, префиксов и суффиксов GUID/типа/индекса. Длина данных и длина имени - разные проверки. Проверяй уникальность, регистр/кодировку, кавычки и ключи отдельно. Не удаляй поля ради прохождения preview без согласования состава с пользователем.
4. Сверь типы и длины с версией приёмника, charset/collation, схемой существующей таблицы/топика, параметрами ключей, индексов и пакетов. SQL-ограничения ниже не заменяют ограничения конкретного драйвера. Если нужные сведения не доступны MCP, укажи непроверенные пункты; запроси диагностику/настройку у администратора вместо выдуманного подтверждения.
5. Для новых имён предложи читаемый короткий алиас со стабильным суффиксом хеша полного пути источника, зарезервировав место для служебных суффиксов. Проверь коллизии всего набора. Сохрани согласованное сопоставление; существующие физические имена не переименовывай автоматически.
6. Наследуй глобальный способ выгрузки ссылок **UUID/GUID либо String**, а также штатную функцию их вычисления. Не определяй ссылку только по имени/SQL-типу. Составные ссылки сохраняют нужные идентификатор и имя типа. UUID/String не основание для автоматического ALTER существующей колонки или смены схемы сообщений.
7. До записи перечисли конкретные проблемы: приёмник, поле, итоговое имя, фактическая длина и её единица (символы/байты/UTF-16), тип/precision/scale, лимит, источник данных об ограничении и предлагаемое исправление. В готовом плане применяй только реально поддерживаемые API-параметры; не добавляй «fieldAliases», «columnTypes» или SQL в неподдерживаемые поля.
8. В компактном создании доступны `selectedFields` и **`guidColumnNames` только для GUID-вычислений**. Произвольные алиасы обычных полей, SQL-типы/длины и DDL через эти параметры не задаются. Для сохранённой отсутствующей таблицы MySQL отдельно поддерживается закрытый вариант существующих preview/update с capability `mysql_receiver_repair`: список подходящих обычных строковых колонок переводится в TEXT, штатное сопоставление остальных полей сохраняется. Точный контракт см. [10-mcp-projects.md](10-mcp-projects.md). Для остальных изменений нужен поддержанный инструмент, ручная настройка 1С либо доработка API. Навык не расширяет контракт и не объявляет предложенное исправление применённым. Ручные изменения перечитай через `verify_project`, затем готовь новый preview; старый planId не переиспользуй.
9. Если API не позволяет корректно выгрузить обязательное поле, останови зависимую запись и дай воспроизводимое задание программисту. Не обходи `СписокТиповПолей`, ошибки драйвера и отказ DDL уменьшением данных, сбросом operationId или записью за пределами MCP. Согласованная минимальная выборка допустима только как отдельный диагностический опыт.
10. После разрешённой записи - `verify_project`. При запуске дождись конечного статуса исходного taskId; принятие команды не равно успешной выгрузке. По доступным разрешённым средствам сверь схему, количество и выбранные значения с приёмником; для Kafka - подтверждённые сообщения. Не называй такую сверку выполненной, если MCP не предоставляет её и независимой квитанции нет.

## MySQL

- Имена БД, таблиц, колонок и индексов - обычно **64 символа**, включая составленные суффиксы. Считай отдельные идентификаторы, а не `database.table` целиком. Кавычки не снимают ограничение; учитывай `lower_case_table_names` и существующие имена.
- `CHAR(n)` - до **255 символов**. `VARCHAR(4000)` сам по себе допустим; максимальный размер строки **65535 байт** делится между колонками и служебными данными. `utf8mb4` требует до 4 байт на символ. Пять VARCHAR(4000) могут дать 1118, хотя одиночная колонка работает. Проверяй также InnoDB page size/row format и индексные ограничения.
- Не вводи универсальный предел VARCHAR=255 и не обрезай значения до 255/4000. Неограниченные/длинные неключевые строки могут требовать TEXT/MEDIUMTEXT/LONGTEXT; прежде проверь поддержку типа во всех путях драйвера. TEXT имеет собственный байтовый предел, это не «неограниченная строка».
- Для ссылок и GUID сохраняй корректное штатное сопоставление Экстрактора, включая вычисляемые колонки с пользовательскими именами. Определяй семантику по маппингу, функции и метаданным, а не по суффиксу. Сохраняй штатный UUID/String-тип и длину; для строкового GUID - 36 символов. При исправлении широкой строки MySQL подбирай TEXT для подходящих обычных строк, не заменяя корректное сопоставление GUID. Если штатный подбор корректен, отдельные запреты и проверки GUID не добавляй.
- Индексированное/сегментное поле нельзя молча перевести в TEXT или индексировать только короткий префикс: это может изменить уникальность и поиск.
- Разделяй: 1059 - слишком длинное имя; 1074 - недопустимая длина типа; 1118 - слишком широкая строка; ошибка длины ключа - ограничение индекса. Не маскируй их отключением strict mode.

Источники: [имена](https://dev.mysql.com/doc/mysql-reslimits-excerpt/8.0/en/identifier-length.html), [CHAR/VARCHAR](https://dev.mysql.com/doc/refman/8.0/en/char.html), [строка и InnoDB](https://dev.mysql.com/doc/refman/8.0/en/column-count-limit.html).

## PostgreSQL

- По умолчанию имя - **63 байта**, не 63 символа; фактический лимит проверяй через `max_identifier_length` и кодировку сервера. Более длинное имя может быть усечено, поэтому не полагайся на успех CREATE как на сохранение полного имени. Проверяй коллизии после усечения и добавления суффиксов.
- Неквотированные имена приводятся к нижнему регистру, квотированные сохраняют регистр. Следуй сохранённой политике драйвера; не вводи несовместимую смену кавычек при обновлении.
- `varchar(n)` ограничивает число символов; `text` не требует произвольного n, но имеет пределы значения/хранения. Нет правила «VARCHAR максимум 255/4000» от другой СУБД. Для длинных данных, numeric(p,s), timestamp/таймзоны и nullable сверяй native mapping и версию.
- Проверяй ограничения индексного ключа и expression/partition keys по фактическому методу индекса и серверу. UUID-режим может использовать uuid, String - строковый тип; не преобразовывай сохранённую колонку без управляемого изменения.

Источники: [имена/кодировка](https://www.postgresql.org/docs/current/sql-syntax-lexical.html), [строковые типы](https://www.postgresql.org/docs/current/datatype-character.html).

## MS SQL

- Обычные идентификаторы - **128 символов**; для временных объектов и служебных суффиксов действуют отдельные ограничения. Проверяй коллизии по collation, схему/таблицу/колонку/индекс отдельно. Не переносить MySQL64/PostgreSQL63 на SQL Server.
- `char(n)`/`varchar(n)` - n до **8000 байт**; `nchar(n)`/`nvarchar(n)` - n до **4000 пар байт UTF-16**. Для emoji число символов может быть меньше n. Unicode/UTF-8 collation и реально используемый ADO-провайдер влияют на корректную передачу данных.
- Для длинных строк рассматривать varchar(max)/nvarchar(max) только при поддержке драйвером и совместимости ключей. Страница строки имеет предел 8060 байт с механизмом row-overflow: не трактуй его как общий запрет суммарных variable-length колонок больше 8060, но проверяй фиксированную часть и ключи.
- Проверяй precision/scale, nullable, длины и ограничение индексных ключей для данной версии/типа индекса. GUID - native uniqueidentifier либо строка согласно глобальной настройке. Изменение существующей схемы требует отдельного плана; при неизвестной/активной выгрузке не запускать DDL.
- При ADO сверяй допустимый форме и установленный ProgID: например, `SQLOLEDB.1`. Успех отдельного COM-подключения не доказывает прохождение формы и полной выгрузки 1С.

Источники: [лимиты SQL Server](https://learn.microsoft.com/en-us/sql/sql-server/maximum-capacity-specifications-for-sql-server?view=sql-server-ver16), [char/varchar](https://learn.microsoft.com/en-us/sql/t-sql/data-types/char-and-varchar-transact-sql?view=sql-server-ver16), [nchar/nvarchar](https://learn.microsoft.com/en-us/sql/t-sql/data-types/nchar-and-nvarchar-transact-sql?view=sql-server-ver16).

## ClickHouse

- Проверяй native правила имён/кавычек, уникальность и регистр. Не назначай выдуманный универсальный лимит 64/63/128. Действующий драйвер/API может ограничивать имя сильнее сервера - учитывай оба контракта. Точки в плоских именах колонок могут конфликтовать с Nested; предлагай алиас с подчёркиванием, не меняя существующую структуру молча.
- `String` не имеет SQL-параметра длины, `FixedString(N)` измеряется в **байтах**, а не символах, и может добавлять нулевые байты. Для переменных Unicode-строк не выбирать FixedString только по числу символов источника. UUID/String сохранять по глобальной настройке.
- Проверяй engine, ORDER BY/PRIMARY KEY/PARTITION BY, nullable-ключи и соответствующие настройки, numeric precision/scale, даты/DateTime64 и таймзону. Таблица создаётся под конкретный engine; тип, допустимый сам по себе, не гарантирует допустимость ключа.
- Сверяй допустимый формат записи, лимиты запроса/пакета и памяти. Не применять SQL Server/MySQL пределы строки к ClickHouse. Для async_insert/Distributed различай принятие, постановку в очередь и фактическую запись; подтверждай результат чтением приёмника.

Источники: [имена/синтаксис](https://clickhouse.com/docs/reference/syntax), [FixedString](https://clickhouse.com/docs/reference/data-types/fixedstring).

## Apache Kafka

- Kafka - приёмник сообщений, не SQL-таблица. Не применять к топику ограничения VARCHAR/CHAR или MySQL64. Для стандартного Kafka topic: непустое имя до **249 ASCII-символов**, допустимы буквы/цифры/`.`/`_`/`-`, запрещены имена `.` и `..`. Проверь версию/контракт используемого коннектора; не создавать служебные топики. Имена с точкой/подчёркиванием могут конфликтовать в метриках - избегай такой неоднозначности для новых имён.
- Отдельно проверяй имена полей и типы по реальному формату сериализации (JSON/Avro/Protobuf/иной), схеме и потребителю. Topic limit не является лимитом имени JSON-поля. Schema Registry учитывать только если он действительно используется; не предполагать его наличие.
- Размер считать для сериализованных key/value/headers и record batch в байтах. Сверять фактические broker/topic/producer/consumer настройки: `message.max.bytes`, `max.message.bytes`, `max.request.size`, `replica.fetch.max.bytes`, `max.partition.fetch.bytes`, `fetch.max.bytes`; их роли и исключения различаются, это не одна общая константа. Если конфигурация недоступна - размер не подтверждён, не подставлять произвольные «1 MB».
- Делить пакет/уменьшать maxItemsPerBatch можно только при сохранении согласованных границ сообщения и семантики потребителя. Не разрезать одну большую запись и не менять схемы, ключ/партиционирование или UUID/String скрытно.
- Проверяй ACL, сериализацию Unicode/Decimal/дат/null/составных ссылок, размер одной записи и всего пакета. delivery acknowledgement не доказывает обработку потребителем; при неизвестном исходе не пересылать сообщение с новым operationId без сверки риска дубликатов.

Источники: [валидация topic в Apache Kafka 3.9](https://github.com/apache/kafka/blob/3.9/clients/src/main/java/org/apache/kafka/common/internals/Topic.java), [producer settings](https://kafka.apache.org/39/configuration/producer-configs/). Для другой версии читать её документацию/фактическую конфигурацию.

## Проверочные случаи для подготовки задания

Проверяй по применимому профилю: длинное имя и коллизии после транслитерации/суффикса, Unicode на границе байтового лимита, широкая таблица, длинное неключевое поле, индекс/сегмент, UUID и String, несовместимая существующая схема. Пробы DDL допустимы только в разрешённой тестовой базе/изолированных объектах, сообщения - в разрешённом тестовом топике. Одни инструкции навыка не означают, что все пять приёмников уже прошли live-тесты.

# Порядок диалога: от установки до проверенной выгрузки

Это сценарий работы существующих MCP-инструментов, а не новая поверхность API.
Начинай с первого незавершённого этапа. Уже заданные базу, маршрут, подключение,
источник, сегменты, префиксы и разрешения сохраняй в диалоге. Не превращай
сценарий в обязательный опрос по всем пунктам: сначала читай доступные настройки,
объединяй связанные вопросы, спрашивай только недостающее.

## Первый запуск AI без предыдущего опыта

Не предполагается ни история диалога, ни знание конкретных баз или проектов.
Ниже минимальная модель работы и первый набор действий.

- MCP - интерфейс команд для AI. Экстрактор установлен внутри базы 1С и
  исполняет команды; его драйвер создаёт таблицы и пишет данные в приёмник.
- Проект - сохранённая настройка выгрузки. В нём могут быть несколько строк:
  каждая задаёт источник, поля, сегменты и свою таблицу назначения.
- Источник - объект 1С, его табличная часть или поддержанная виртуальная таблица
  регистра. Пользовательское название сначала сопоставляется с метаданными.
- Сегмент определяет части очереди выгрузки. Он не заменяет периодичность
  виртуальной таблицы, отбор данных или ограничение общего числа записей.
- GUID связывает записи разных таблиц. Представление ссылки - читаемый текст,
  который не заменяет GUID и не доказывает связь объектов.

После установки:

1. Получи фактический список инструментов подключённого MCP. Не придумывай
   названия или аргументы методов по примерам из другого выпуска.
2. Вызови `list_skills`. Найди навык Экстрактора в возвращённом каталоге и
   передай его фактический `id` в `get_skill(skill_id=..., document="SKILL.md")`.
   Затем прочитай этот документ через `get_skill` и нужные документы этапа из
   того же каталога. Навык с диска не доказывает, что MCP подключён и отвечает.
3. Вызови `list_bases`. Это доступные выбранному экземпляру MCP базы.
   Не подставляй адреса и `base_id` из примеров или чужого окружения.
4. Выбери базу по заданию пользователя; при неясности покажи список и уточни.
   Передавай один и тот же `base_id` во все действия по этой базе.
5. Вызови `readiness(base_id=...)`. Проверь `ready`, фактические версии,
   capabilities и предупреждения. Не продолжай запись через недоступный или
   несовместимый маршрут; не подставляй локальную версию вместо ответа базы.
6. Вызови `list_connections(base_id=...)`, покажи список и проверь выбранный
   приёмник по следующему разделу. Затем узнай, что выгружать.

Если инструменты не подключены или отказывают в авторизации, сначала исправь
установку по CONFIG, не имитируй ответы MCP. Если нет capability нужной функции,
не используй похожий метод для обхода ограничения. Политика безопасности,
строгие схемы параметров и права пользователя действуют при обоих маршрутах.

Если пользователь просит именно установить систему, начни со следующего
раздела; если всё установлено, выполняй проверку первого запуска, не переустановку.

## Установка и развёртывание

Сначала проверь доступную установку, `list_bases`, версии и capabilities через
`readiness`. Версия платформы, версия Экстрактора и версия API - разные факты.
Для старой платформы проверяй доступность способа установки и компиляцию;
не обещай поддержку расширения только по версии API. Используй существующие
инструкции [развёртывания](20-deployment-architecture.md) и [CONFIG.md](../CONFIG.md).

Вопросы, только если ответ ещё неизвестен:

1. «С какой базой 1С работаем?» Покажи обнаруженные базы; уточни точную базу
   при совпадении названий. Файловый/серверный вариант и платформу сначала
   устанавливай по доступным настройкам, без повторного вопроса пользователю.
2. Если установка нужна: «Где должен работать MCP: локально или на сервере?»
   Существующее рабочее развёртывание само по себе не повод переносить сервер.
3. При доступности обоих маршрутов: «Работаем напрямую через публикацию 1С
   или через DCC?» Сохраняй выбор; смена маршрута после ошибки не автоматическая.
4. Если необходимо участие пользователя в установке: уточни способ применения
   подготовленных модулей. Действуй самостоятельно в уже разрешённых базах и
   окружениях; не запрашивай повторное согласие на ранее разрешённое обновление.

Пароли и токены в диалоге не запрашивай. При необходимости используй настроенный
способ хранения секретов. Не создавай канал выполнения произвольного BSL.

## Проверка подключений и показ пользователю

Прочитай `list_connections`. Покажи название и тип каждого подключения; не
показывай пароли, токены и строки подключения с секретами. Список должен быть
живым, а не взятым из старого примера.

1. Подключений нет: сообщи, какой настройки не хватает в Экстракторе, и после
   её появления перечитай список.
2. Подключение одно: покажи выбранное подключение и используй его без лишнего
   вопроса, если оно соответствует заданному пользователем приёмнику.
3. Подключений несколько и выбор неизвестен: «В какое подключение выгружать?»
   Предложи фактические названия с типами. Ранее выбранное подключение используй
   повторно; исчезнувшее или неоднозначное имя требует уточнения.
4. Проверь соединение с приёмником со стороны 1С штатным поддержанным способом.
   Для существующего проекта на этом подключении допустим `inspect_project_receiver`.
   `readiness.ready=true` эту проверку не заменяет. Не создавай пробный проект
   ради проверки подключения; не подменяй отсутствующий метод произвольным SQL/BSL.

До успешной проверки приёмника не переходи к записи проекта. При проблеме
покажи конкретный отказ и выполни разрешённое исправление; технические решения
не перекладывай на пользователя, если информации достаточно.

## Что пользователь хочет выгрузить

Первый содержательный вопрос: «Что хотите выгрузить: справочник, документ,
регистр или другой объект? Можно назвать объект и нужные данные своими словами».
Если источник уже назван, сразу ищи его через `search_metadata` и уточняй только
неоднозначность. Для выбора полей используй `describe_object_fields`.

Показывай только источники и варианты данных, подтверждённые метаданными,
capabilities и живым предпросмотром этой базы. Не обещай неподдержанную функцию
из-за её наличия в платформе или в другом выпуске Экстрактора.

## Вопросы по сущности: порядок

Внутри выбранной сущности порядок такой: конкретный источник и состав строк
проекта; затем смысл и детализация данных; затем сегментация; затем поля и связанные объекты.
Затем применяются общие вопросы об именах и действиях после создания.

| Сущность | Последовательность вопросов |
|---|---|
| Справочник | Какой справочник? Затем нужны элементы, табличные части или оба варианта? Затем сегмент по ссылке или по первым буквам наименования/кода? При расширенной схеме отдельно уточни сегмент инициализации. Затем какие поля и связанные справочники нужны? |
| Табличная часть справочника | Какой справочник и какая табличная часть? Затем Нужна ли отдельная строка выгрузки самого справочника? Затем Сегмент по ссылке владельца или его наименованию/коду? Затем При расширенной схеме отдельно регулярный сегмент и сегмент инициализации; затем Какие поля табличной части нужны? |
| Документ | Какой документ? Затем Шапка, какие табличные части, либо всё вместе? Затем Сегмент по дню или по ссылке документа? Затем При расширенной схеме отдельно регулярный сегмент и сегмент инициализации; затем Какие поля и связанные справочники нужны? |
| Табличная часть документа | Какой документ и табличная часть? Затем Выгружать шапку в том же проекте? Затем Сегмент по дню документа или по ссылке владельца? Затем При расширенной схеме отдельно регулярный сегмент и сегмент инициализации; затем Какие поля строк нужны? |
| Регистр накопления | Какой регистр? Затем нужны обороты, движения или другой подтверждённый вариант? Обороты предлагай первым, если подходят задаче. Затем какая детализация оборотов нужна? Затем регулярный сегмент; при расширенной схеме отдельно сегмент инициализации. Затем какие ресурсы, измерения и связанные сущности выгружать? |
| Периодический регистр сведений | Какой регистр? Затем Нужна история записей или доступный срез? | Непериодический регистр сведений | Какой регистр? Затем Какие измерения и данные нужны? Затем По какому подтверждённому полю разбивать данные, либо выгружать целиком, если такой режим поддержан? Затем При расширенной схеме отдельно обе роли; затем Нужны связанные сущности? Дату или регистратор не предполагаем без метаданных. |

| План видов расчёта | Какой план? Затем Какие виды расчёта, поля и доступные табличные части нужны? Затем Сегмент по ссылке или другому подтверждённому полю? Затем При расширенной схеме отдельно обе роли; затем Нужны связанные регистры и сущности? |
| Перечисление | Какое перечисление? Затем Нужны все значения и их штатные идентификаторы/представления? Обычно отдельная небольшая таблица без сегментации; вопрос о сегменте не навязывай. |
| Бизнес-процесс | Какой бизнес-процесс? Затем Какие поля и доступные части нужны? Затем Сегмент по фактической дате или ссылке, если доступны? Затем При расширенной схеме отдельно обе роли; затем Нужны связанные задачи и справочники в этом проекте? |
| Задача | Какой вид задач? Затем Какие поля и доступные части нужны? Затем Сегмент по фактической дате или ссылке, если доступны? Затем При расширенной схеме отдельно обе роли; затем Нужен связанный бизнес-процесс? |

| Журнал документов | Какой журнал? Затем Какие доступные поля и ссылки на документы нужны? Затем Сегмент по подтверждённой дате или иному полю? Затем При расширенной схеме отдельно обе роли; затем Нужны сами документы? Сначала проверь наличие журнала и поддержку источника в этой базе. |

Для констант и произвольных запросов 1С сначала проверь поддержку существующим
контрактом. Если её нет, явно сообщи ограничение: вопросы об их настройках не
означают, что такой проект уже можно создать. Не предлагай обход через Выполнить(),
Вычислить(), входящий BSL или исполняемые шаблоны. Запросы и отборы, которых нет
в типизированном контракте, не добавляй в неподдерживаемые поля.

## Обязательные правила сегментации

Для регистра накопления спроси сегменты, предлагая **День для регулярной
выгрузки, Месяц для инициализации**; детализация оборотов - **Регистратор**.
Сохраняй уже согласованный другой вариант. Для регистра сведений сначала
подтверди доступность `СрезПоследних`, затем предложи **Месяц**. Если месячные
сегменты велики (цены номенклатуры, товары, партии), спроси дополнительное
поле сегментации и подтверди его по метаданным до подготовки проекта.

Для подобных справочников сначала предложи расширенную схему: регулярная
`Ссылка` с упаковкой `1000`, инициализация по первым двум буквам `Наименование`.
Поля и функции проверь по этой базе; подробности в
[16-catalog-document-segments.md](16-catalog-document-segments.md). Уже выбранную
схему сохраняй. Этот вариант не задаёт сегментацию других видов сущностей.

- Один способ сегментации - простая схема. Не включай расширенную только
  ради инициализации. Для простого режима используй штатное поведение
  инициализации по регулярному сегменту; не создавай лишнюю отдельную роль.
- При расширенной схеме спроси по порядку: «Какой сегмент для регулярной
  выгрузки?»; затем «Какой сегмент для инициализации?». Для регулярной часто подходят
  ссылка/регистратор или день; для инициализации обычно нужен более крупный
  сегмент, например месяц/квартал/год для даты. Показывай варианты по типу поля
  и поддержке API. Если подходящий крупный сегмент непонятен - уточни.
- Третью роль `extended` уточняй только когда она действительно нужна; наличие
  расширенного режима не означает обязательного отдельного третьего сегмента.
- Если пользователь уже назвал разные регулярный и начальный сегменты, схема
  уже определена: не спрашивай ещё раз «простая или расширенная».
- Для ссылки каталога/документа используй штатную упаковку по 1000; это размер
  пакета, а не ограничение общего объёма. Для даты табличной части документа
  подтверждай путь `Ссылка.Дата`, а не подставляй поле строки `Дата`.
- Детализация оборотов и сегмент партицирования - разные настройки. «По дням»
  не означает автоматически, что можно изменить периодичность оборотов или
  потерять регистратор. При неоднозначности уточни требуемое зерно результата.
- В файловой базе учитывай ограничение выполнения; не предлагай пользователю
  несколько параллельных потоков выгрузки.

## Поля и связанные строки проекта

Сначала предложи состав, соответствующий задаче. Для документов и регистров ссылочные поля
обязательны: сохраняй штатные GUID, а для составных ссылок - также тип сущности.
До подготовки проекта обязательно спроси: **«Показывать представления ссылочных полей
в регистре/документе - да или нет?»**, предлагая «Нет». Уже данный ответ
не переспрашивай. При «Да» включай представления; при «Нет» отмечай их
«Не выгружать» (`НеСоздаватьПоле`) штатным механизмом, сохраняя строки
сопоставления; покажи выбор в плане. Не подменяй признак удалением строк
через `selectedFields`. Если контракт не позволяет передать выбранный режим,
сообщи ограничение, не подменяй ответ пользователя и не придумывай параметр API.
Не выбрасывай обычные поля
или ресурсы из-за ошибки схемы приёмника.

Для справочников представления ссылок по умолчанию оставляй вместе со штатными
идентификаторами. Правило отключения из предыдущего абзаца относится к документам и регистрам.

Для GUID и ссылок используй штатное сопоставление Экстрактора. Их семантика
устанавливается по маппингу, функции и метаданным; UUID/String-режим, корректный
штатный тип и длина сохраняются. При исправлении широкой строки подбирай TEXT
для подходящих обычных строк, не подменяя штатное сопоставление GUID. Если оно
корректно, отдельный запрет или специальную проверку GUID не добавляй.

Используй по максимуму штатный помощник Экстрактора для источника, вычислений
и маппинга. Выгружай GUID всех ссылочных полей через штатную функцию
`УникальныйИдентификатор`; для этих GUID в SQL-сопоставлении снимай
«Экранировать». При выбранном «Нет» представления оставляй отдельными невыгружаемыми строками.
Проверяй конкретную функцию и исходное ссылочное поле, сохраняя штатные
тип/длину GUID и типы составных ссылок; имя с суффиксом GUID само по себе
не доказывает семантику.

Связи раскрывай через `analyze_reference_graph`, показывай дерево. Если
справочник связан с фактом через ключи аналитики, покажи и предложи промежуточные
таблицы до полной цепочки к выбранным сущностям. В подтверждённом примере
выручки и себестоимости нужны обе аналитики: учёта номенклатуры и учёта по
партнёрам. Не переноси эти имена в другую конфигурацию без проверки графа.
Не называй прямой связь, которая фактически проходит через промежуточную сущность.
Для принятых связей сохраняй одинаковые имена ключей с обеих сторон.
Режим `account_scope` выбирает область анализа связей по счетам; он не означает
автоматический отбор записей выгрузки по этим счетам.

## Общие вопросы перед записью

После выбора состава и сегментов спроси только недостающее:

1. «Как назвать проект и какой префикс использовать?»
2. «Какой префикс таблиц назначения? Такой же, как у проекта, или другой?»
3. Покажи итог: база, маршрут, подключение, источники и промежуточные таблицы,
   поля/ключи, простая или расширенная схема, обе роли при расширенной схеме,
   периодичность виртуальных таблиц, имена назначения. Разреши выявленную
   неоднозначность до записи, а не отдельными догадками после создания.

Для SQL при capability `direct_sql_operations` выполни разрешённое создание
непосредственно по согласованному определению с `operation_id`, без preview.
Штатную проверку определения выполняет Экстрактор внутри операции; после неё
перечитай проект и схему приёмника. Для Kafka, AMQP и 1С Шины сначала сделай
preview и прочитай все страницы плана. Если конкретное создание уже разрешено
и соответствует запросу, не требуй повторного согласия. Сохранённые
`operationId` и, при использовании плана, `planId` не подменяй после таймаута.

## После создания и проверки

Отдельно подтверди настройки проекта и наличие/соответствие таблиц приёмника.
Таблицы создаёт Экстрактор 1С через штатный драйвер; MCP передаёт типизированную
команду. Успешная запись настроек при ошибке DDL не считается полностью готовым
проектом. При восстановлении отсутствующей таблицы существующие не пересоздавай.

Только ещё не заданные решения собери в один короткий блок:

1. «Инициализировать очередь проекта?»
2. «Запустить выгрузку сейчас?»
3. Если запуск выбран: «Дождаться завершения?»
4. «Нужно расписание? Если да - дни, время или интервал и часовой пояс».

Пользователя выполнения бери из общих настроек Экстрактора. Инициализация,
запуск и включение расписания - отдельные действия. Не утверждай успешную
выгрузку по принятию команды: дождись `status: succeeded`, если ожидание задано,
и сообщи фактические результаты проверки приёмника и их ограничения.

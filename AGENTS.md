# Правила работы с репозиторием

Эти правила предназначены для любых ИИ-агентов и участников разработки.

Основной репозиторий: [Denvic-Tech/extractor-mcp-server](https://github.com/Denvic-Tech/extractor-mcp-server).

## Область проекта

Репозиторий содержит Python MCP-сервер, поставляемые клиентские навыки,
инструменты установки и публичную документацию. Сервер связывает
MCP-совместимые ИИ-клиенты с API Экстрактора 1С напрямую или через DCC.

Перед настройкой или запуском прочитайте
[порядок развёртывания и установки](docs/Справочник/installation.md)
и [подключение ИИ-клиента](docs/Справочник/client-connection.md).

## Работа с изменениями

- Проверьте ветку и состояние рабочего дерева. Используйте ветку, указанную
  пользователем; сохраняйте существующие изменения.
- Вносите только изменения, необходимые для задачи. Сначала изучите
  соответствующий код, тесты и документацию.
- Сохраняйте совместимость публичных инструментов и параметров.
  Изменения контракта описывайте в публичной документации.
- Не храните в Git рабочие настройки, учётные данные, токены, локальные
  базы состояния, логи и результаты запусков.
- Не выполняйте commit, push, публикацию или развёртывание за пределами
  разрешённого пользователем объёма. Переписывание истории требует
  отдельного явного разрешения.

## Структура и зависимости

- `mcp/src/extractor1c/domain/` - модели и правила без ввода-вывода.
- `mcp/src/extractor1c/application/` - сценарии и порты внешних зависимостей.
- `mcp/src/extractor1c/infrastructure/` - транспорт, настройки и хранение состояния.
- `mcp/src/extractor1c/interface/` - инструменты MCP, HTTP-приложение и запуск.
- `mcp/skills/` - встроенные инструкции, доступные через MCP.
- `mcp/plugins/` - клиентский плагин.
- `mcp/tests/` - тесты сервера.
- `docs/` - публичная документация.

Зависимости направлены внутрь: `interface -> application -> domain`.
Адаптеры инфраструктуры реализуют порты приложения.
Инструменты MCP оставляйте тонкими; логику размещайте в соответствующем слое.
Сохраняйте точки входа `mcp_server.py` и `secure_main.py`.

## Проверка

Используйте Python 3.11+ и зависимости разработки из `mcp/pyproject.toml`.
После изменения сервера выполните из `mcp/`:

```text
python -m pytest -q
python -m ruff check src tests scripts
```

Здесь `python` - интерпретатор виртуального окружения проекта.
На Windows это `mcp\.venv\Scripts\python.exe`, на Linux/macOS -
`mcp/.venv/bin/python`, если окружение создано в `mcp/.venv`.

Имена, параметры, аннотации инструментов и серверные инструкции проверяются
`mcp/tests/test_tool_contract.py`. При осознанном изменении контракта
обновите снимок командой, указанной в заголовке теста.

Не запускайте проверки параллельно с общим временным каталогом.
Для документации проверьте относительные ссылки и `git diff --check`.
Сообщайте реальные результаты: что прошло, что пропущено и что осталось
непроверенным. Живые проверки выполняйте только в согласованном окружении.

## Документация и поставка

Пишите публичную документацию на русском, кратко и понятно.
Используйте Markdown, совместимый с GitHub и Gramax.
Корневой README содержит описание, быстрый старт и навигацию;
подробные инструкции размещаются в `docs/`.
Сохраняйте действующие идентификаторы навыков и обновляйте ссылки
после перемещения документов.

Перед публикацией проверьте состав изменений. В репозиторий должны попадать
только файлы продукта и публичная документация, без внутренних адресов,
служебных материалов и секретов. Соблюдайте процесс проверки и публикации,
принятый в репозитории.

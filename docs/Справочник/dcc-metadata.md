# Метаданные и операции через DCC v2

В режиме `EXTRACTOR_PROJECTS_TRANSPORT=dcc` MCP соединяется только с DCC.
1С сама получает команды обычным `tasks/pending` и отправляет результаты.
Web-публикация 1С и сетевой маршрут MCP → 1С для этого режима не нужны.

## Чтение сохранённых метаданных

| Инструмент MCP | Что возвращает |
|---|---|
| `get_metadata_snapshot` | Происхождение снимка, `snapshotId`, полнота и предупреждения |
| `search_metadata` | Страница списка имён объектов; подробности в `objectDescriptions` |
| `describe_object_fields` | Страница полей одного объекта, альтернативы типов и ссылочные назначения |
| `analyze_reference_graph` без `account_scope` | Граф и дерево сохранённого снимка с ограничениями обхода |

Страница — ограниченная часть списка, а не отдельный объект. Ответ содержит
`total` и `nextCursor`. Для продолжения передайте `nextCursor` как `cursor`,
а прежний `snapshotId` — как `snapshot_id`. Без явно указанного снимка каждый
запрос выбирает текущий снимок; последовательные страницы могут относиться к
разным версиям. Истёкший явно указанный снимок не заменяется новым молча.

Фильтры и пагинация выполняются DCC. Полная конфигурация не передаётся MCP
для поиска одного объекта. Составные типы, квалификаторы и предупреждения
сохраняются. Поля виртуальной таблицы могут быть приближением по метаданным
регистра: учитывайте `metadataEnriched`, `virtualTable` и `objectWarnings`.

Граф с `account_scope` требует назначенных субконто из живой 1С. Он использует
задачи MCP в DCC; параметр `snapshot_id` с этим режимом не поддерживается.
Это обращение через исходящий обмен 1С, а не прямой HTTP-вызов её публикации.
Полные совместимые методы `list_metadata` и `describe_object` также используют
задачи DCC; для повседневного поиска предпочтительны компактные инструменты.

## План проекта и подтверждение

1. Выберите `base_id` из `list_bases`.
2. Прочитайте снимок, найдите объект, поля и нужные связи в том же снимке.
3. Передайте `snapshotId` как `metadata_snapshot_id` в `preview_project`
   или `preview_project_template`.
4. MCP проверяет наличие снимка и выполняет окончательный `projects/preview`
   задачей DCC в целевой 1С. Снимок сам по себе не доказывает корректность
   запроса, вычисляемых полей или схемы приёмника.
5. Одобренный план сохраняет `metadataEvidence`; она доступна через
   `get_project_plan`. Происхождение не добавляется в payload бизнес-метода 1С.
6. После разрешения пользователя примените прежний `plan_id` и новый UUID
   `operation_id`. Для проверки результата используйте тот же `base_id`.

`metadata_snapshot_id` необязателен. Если он не передан, preview работает
через прежний транспорт задач. Снимок — свидетельство происхождения плана,
а не запрет изменения конфигурации после preview и не замена бизнес-проверок 1С.

## Ожидание и сбои

- `queued` и `running` означают незавершённую операцию; ждать можно оба состояния.
- Тайм-аут и потеря ответа сохраняют прежний `operation_id`.
- `get_operation_status` читает состояние и не ставит новую задачу.
- Связь операции, метода и `task_id` сохраняется до начала ожидания и проверяется
  после перезапуска MCP. Подмена задачи не завершает прежнюю операцию.
- Ошибка или неопределённый исход изменяющей команды сохраняют локальный запрет
  повторного исполнения. В блоке `dcc` возвращаются удалённый статус, результат
  и диагностика; чтение не снимает запрет автоматически.
- При истечении JWT клиент один раз выполняет новый вход. Повтор отправки
  операции сохраняет то же тело и `Idempotency-Key`. Новый UUID не создаётся.
- `completed` операции запуска означает результат обработки запроса запуска.
  Завершение выгрузки проверяется отдельно по возвращённому taskId.
- Автоматического перехода на прямой HTTP или DCC v1 нет. Long polling отложен.

Прямой HTTP остаётся отдельным режимом с базами из `bases.yaml`;
параметры снимка DCC в нём отклоняются.

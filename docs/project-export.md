# Запуск и состояние выгрузки проекта

Реализация находится в MCP и отдельном расширении `ExtractorProjectsAPI`.
Исходники Экстрактора 1С не изменяются. API вызывает существующий
`Экс_МодульВыгрузки.ВыгрузитьПроект` с актуальной сигнатурой и запуском в фоне.
Штатные HTTP `НачатьВыгрузку` / `СтатусВыгрузки` не используются: первый
рассчитан на старый контракт запуска, второй по умолчанию удаляет сообщения ФЗ
и не связывает переданный идентификатор задания с проектом.

## MCP

1. Найти проект через `list_projects`, получить `projectRef` через `verify_project`.
2. `preview_project_export(project_guid)` возвращает `planId`, срок действия и
   `summary`: проект, текущее выполнение, HTTP-пользователь запуска, блокировки,
   предупреждение о немедленном выполнении.
3. Показать пользователю план запуска всего проекта. При наличии разрешения
   вызвать `start_project_export(plan_id, operation_id)` с новым UUID операции.
4. Сохранить `result.taskId` и читать
   `get_project_export_status(project_guid, task_id)` до итогового состояния.

Выгрузка идёт по сохранённым настройкам и очереди всех строк проекта.
Расписание не меняется, очередь не сбрасывается. Существующие обработчики
проекта могут выполняться в рамках штатной выгрузки. Фоновое задание запускается
под текущим HTTP-пользователем, а не пользователем регламентных заданий.
Проверяется штатное право изменения проектов или роль `Экс_ВыполнениеПроектов`.
Лицензирование выполнения остаётся в штатном механизме Экстрактора. Проверка
`dateDue` для сохранения настроек не переносится на запуск.

`launchStatus` описывает ответ на запрос запуска:

| Значение | Смысл |
|---|---|
| `started` | Задача и ФЗ созданы, их связь с проектом перечитана; выгрузка ещё может завершиться ошибкой |
| `already_running` | Штатный метод обнаружил уже выполняющуюся выгрузку |
| `initializing` | Штатный метод обнаружил выполняющуюся инициализацию |
| `rejected` | Запуск не выполнен: план устарел, действует запрет или занята блокировка |
| `unknown` | Создание запуска не подтверждено; MCP сохраняет неопределённый результат |

`taskId` обозначает запись `Экс_Задачи`, `backgroundJobId` - фоновое задание
конкретного выполнения. Это не `jobId` регламентного задания из расписания.
`get_operation_status` описывает обработку запроса MCP: его `completed`
не означает завершения выгрузки. Отказ `launchStatus: rejected` тоже является
завершённым запросом с сохранённым ответом, без нового запуска.

## Чтение выполнения

Статусы: `idle`, `pending`, `running`, `succeeded`, `failed`, `cancelled`,
`unknown`, `not_found`. В ответе есть проект, идентификаторы задачи и ФЗ,
`taskType`, `nativeStatus`, время начала/окончания в UTC миллисекундах,
`message` (до 4000 символов) и `warnings`.

Запрос фильтрует задачу по проекту и разрешённому типу. Чужой или удалённый
`taskId` возвращает `not_found`. Без `task_id` выбирается последняя выгрузка
с приоритетом записи `Выполняется`; этот режим предназначен для обзора,
а не для доказательства результата конкретного HTTP-запроса. Штатная очистка
может удалять задачи старше трёх дней.

Чтение не изменяет регистр и не забирает сообщения ФЗ:
`СостояниеФоновогоЗадания(id, Ложь, Ложь)`. Сохранённый итог задачи имеет
приоритет. Завершение ФЗ без итогового состояния задачи не считается успехом.
Отсутствие ФЗ или невозможность прочитать его состояние дают `unknown`.
Проект должен оставаться доступным в области API, без пометки удаления и
с непустым составом источников; иначе чтение возвращает ошибку API.

## Повторы и конкурентные изменения

План хранит неизменяемые `projectGuid` и `expectedProjectState` (версия данных
проекта и HTTP-пользователь). Перед запуском API повторяет предпросмотр и
сравнивает токен. Штатный запуск сам управляет транзакциями и блокировками;
внешняя транзакция вокруг него не создаётся. Между сверкой и штатным запуском
остается окно изменения проекта через интерфейс 1С: не редактировать настройки
одновременно с запуском. Запрет ресурсов и право запуска проверяются снова.

Завершённый `operationId` возвращает сохранённый ответ, без HTTP-запуска.
Обрыв связи, некорректный ответ или `unknown` дают `indeterminate`. MCP блокирует
новые планы запуска того же проекта, пока в общем хранилище есть `in_progress`
или `indeterminate` для выгрузки или [инициализации очереди](project-initialization.md).
Блокируются оба вида запуска; новый UUID и перезапуск сервера не обходят блокировку.
Несколько экземпляров MCP должны использовать одно постоянное хранилище.
Нативная блокировка дополнительно защищает от одновременного выполнения.

При неопределённости прочитать `get_operation_status`, затем состояние задачи
по известному `taskId` и журнал 1С. Одно чтение статуса не снимает блокировку.
Автоматического сопоставления потерянного ответа с последней задачей и
автоматического повторного старта нет. Снятие такой блокировки требует
администраторской сверки и восстановления записи операции из подтверждённого
результата; публичной команды принудительного сброса нет. Не удалять SQLite
и не создавать новое хранилище ради повторного запуска.

## Фиксированный API и установка

Все маршруты - POST JSON относительно `/hs/extractor-projects/v1`:

| Маршрут | Поля тела |
|---|---|
| `projects/export/preview` | `projectGuid` |
| `projects/export/start` | `projectGuid`, `expectedProjectState` |
| `projects/export/status` | `projectGuid`, необязательный `taskId` |

Произвольные URL, код, SQL и дополнительные поля отвергаются. Клиент не
повторяет HTTP-запуск автоматически. Идемпотентность обеспечивается MCP,
а не прямыми вызовами API. Не вызывать маршрут запуска в обход MCP.

Обновить Экстрактор 1С начиная с 3.16.1.xx из коммерческой поставки [«Экстрактор данных 1С в BI»](https://bi.denvic.ru/) и MCP 3.2.0. Методы EPA_Projects должны сообщать 3.2.0. Проверка компиляции и выполнения в целевой базе обязательна. В DCC-режиме запрос выполняется через задачу DCC с тем же прикладным контрактом и возвращаемым taskId; публикация 1С напрямую не вызывается.

После публикации в тестовой базе проверить права HTTP-пользователя, разбор
запроса регистра, preview без запуска, реальный запуск согласованного проекта,
привязку taskId к проекту, повтор операции, несколько чтений успешного и
ошибочного результата, отсутствие удаления сообщений и конкурентный запуск.
Автотесты Python проверяют протокол и защиту от повторов с подменённым API;
они не подтверждают исполнение BSL платформой 1С.
